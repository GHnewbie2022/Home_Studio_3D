Loading 瓶頸調查與優化方案

2026-05-20 ｜ R7-3.10 靜態漫射烘焙擴張期間 ｜ 診斷報告 + 優化提案

一、症狀描述

開啟 http://localhost:9001/Home_Studio.html 時，loading 圓圈動畫會顯示到 5～6% 後卡住好幾秒，然後才繼續上升到 100%。

三、根因分析

進度條公式

// InitCommon.js L209
var progress = 0.08 + 0.90 * (ready / total);
// total = 22, ready = 0 → 顯示 8%（動畫插值中先經過 5%、6%）
// 每完成 1 面 → +4.09%

在第一個面載入完成之前，進度值固定在 8%，所以使用者看到 5～6% 的動畫插值後就停住。

啟動時間軸

階段 A — JS 腳本解析
InitCommon.js 517KB + Home_Studio.js 384KB 解析
≈ 50～100 ms（不是瓶頸）
階段 B — Shader 檔案載入 + 編譯
Home_Studio_Fragment.glsl 255KB 透過 fileLoader.load() 載入，Three.js 在首次 render() 時觸發 WebGL compile + link，主執行緒被鎖住
≈ 2～5 秒（GPU-bound，主執行緒凍結）
階段 C — 22 個 bake 面並行下載
每面三段串行 fetch（pointer JSON → validation JSON → 16MB atlas bin），全部帶 cache: 'no-store'。HTTP/1.1 最多 6 連線同時下載
≈ 3～10 秒（取決於 server 與磁碟 I/O）
階段 D — atlas 合成（重複 22 次）
每完成 1 面就呼叫 refreshR7310C1CombinedDiffuseRuntimeTexture()，分配 384 MB Float32Array 並逐像素複製 22 個 slot
≈ 每次 200～500 ms × 22 次

階段 B 和 C 時間重疊，但 shader 編譯期間主執行緒被鎖住，即使 fetch 回來了也無法執行 callback，進度條動畫凍結。這就是使用者看到「卡在 5～6%」的直接原因。

涉及檔案

檔案 角色 大小
js/InitCommon.js loading 進度條邏輯、22 個 bake loader、atlas 合成、cache: 'no-store' 設定 517 KB
shaders/Home_Studio_Fragment.glsl path tracing 主 fragment shader（WebGL 編譯瓶頸來源） 255 KB
assets/bakes/r7-3-10/c1-static-diffuse/*/atlas-patch-000-rgba-f32.bin 22 個 bake atlas 二進位檔案 各 16 MB
docs/data/r7-3-10-c1-*-runtime-package.json 22 個 pointer JSON 各 1～2 KB

四、優化方案

第一層：低風險、高回報

方案 1：移除 cache: 'no-store'，改用帶版本號的 URL 低風險 最高回報

現況：66 個 fetch 全部帶 { cache: 'no-store' }，每次開頁面都重抓 352 MB。

做法：atlas bin 的 URL 加上 cache-buster query string（跟 CSS / JS 已經在做的一樣，例如 ?v=r7310-xxx），移除 cache: 'no-store'。瀏覽器第二次開啟後直接從 disk cache 讀取。

預估改善：第二次以後載入從數秒降到幾乎為零。第一次載入不變。

改動範圍：InitCommon.js 中約 44 處 fetch 呼叫的 option，加上 URL 拼接改用版本號。

方案 2：延遲 atlas 合成（只在全部到齊後做一次） 低風險

現況：refreshR7310C1CombinedDiffuseRuntimeTexture() 在每個面載入完成後都呼叫一次。22 面 = 重建 22 次，每次分配 384 MB。

做法：收到一個面 → 存起來 → 更新進度條 → 不合成。等全部到齊後做一次。

預估改善：合成從 22 次降到 1 次。減少約 21 × 384 MB 記憶體分配與逐像素複製。

副作用：loading screen 期間 partial bake 不會即時生效，但使用者看不到。

方案 3：進度條加入下載細粒度 低風險

現況：進度只在「面完成」時跳一格（每格 4%），下載 16 MB bin 期間沒有中間回報。

做法：拆分三段 fetch 分別回報進度；或用 response.body.getReader() 逐塊讀取 bin 檔案，根據已讀位元數回報中間百分比。

預估改善：視覺感受大幅改善，進度條持續在動。

第二層：中等風險、高回報

方案 4：並行下載重構 中風險

現況：每面的三段 fetch 嚴格串行。22 面之間雖並行，但 HTTP/1.1 最多 6 連線同時。

做法：

A. Promise.all 一次拿 22 個 pointer JSON
B. Promise.all 一次拿 22 個 validation JSON
C. Promise.all 一次下載 22 個 atlas bin

額外可搭配 HTTP/2 server（如 npm http-server --ssl）解除 6 連線上限。

預估改善：下載總時間取決於最慢的單一 bin，而非串接延遲。

方案 5：Shader 編譯不阻塞進度動畫 中風險

現況：Three.js 在首次 renderer.render() 時觸發 WebGL shader compile，主執行緒被鎖住數秒，進度條凍結。

做法（兩個方向）：

A. 使用 KHR_parallel_shader_compile 擴充功能
   Three.js r150+ 支援。Shader 在 GPU 背景編譯，主執行緒不被鎖住。

B. 在 loading screen 顯示期間先呼叫 renderer.compile(scene, camera)
   把 shader 編譯提前到 loading 階段。

預估改善：消除進度條凍結的體感。

第三層：大工程、長期考量

方案 6：atlas bin 壓縮格式 高風險

現況：每個 atlas 是 raw RGBA Float32，1024² × 16 bytes = 16 MB。

做法：儲存為 RGBE（每像素 4 bytes）或 Float16（每像素 8 bytes），runtime 解碼。

預估改善：下載從 352 MB 降到 88～176 MB。

風險：需要修改 bake pipeline 輸出格式、shader 解碼邏輯、驗證視覺品質。

方案 7：預合成單一 atlas 檔案 高風險

現況：runtime 下載 22 個獨立 bin 後在 JS 端逐像素合成一張 6144×4096 的合併貼圖。

做法：bake 完成後用 Node.js 工具預先合成 combined-atlas.bin，runtime 一次 fetch 直接使用。

預估改善：省掉 JS 端合成步驟。搭配方案 6 的壓縮格式效果更好。

風險：需要新增 build 工具，維護「重烘焙 → 重合成」流程。

五、推薦優先順序

優先 方案 風險 改動量 預估效果
1 移除 cache: 'no-store' 低 ~44 行 第二次載入接近瞬間
2 延遲 atlas 合成 低 ~30 行 省 21 次 384 MB 重建
3 進度條細粒度 低 ~50 行 進度條持續在動
4 提前 shader compile 中 ~10 行 消除凍結感
5 並行下載重構 中 ~200 行 首次載入加速 30～50%
6 壓縮格式 / 預合成 高 大工程 下載量減半以上
建議：方案 1 + 2 + 3 三個合在一起做，改動量小、風險低。第二次以後開啟頁面的載入等待應該從「卡在 5% 好幾秒」變成「幾乎瞬間到 100%」。
