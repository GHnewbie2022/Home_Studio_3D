R7-3.10 北牆提高 D 試驗計畫

0. 目前共識

北牆非方格烘焙已經證明一件事：髒斑的方向性拉伸已消失，代表「照牆面真實比例分配 texel」這條路有效。 現在剩下的問題是：髒斑仍然太粗，看起來像一塊被放大的雜訊紋理。

本計畫只處理「髒斑粗度」。 髒斑濃淡已知可以用 10000 SPP 降低，這次不重複驗證。 這次先用 1000 SPP 測 D，保留足夠雜訊，讓粗度差異容易被看見。

1. 為什麼先提高 D

D 是「每公尺牆面分到多少烘焙 texel」。

D 越低：
  一個 texel 對應牆上較大面積。
  髒斑容易像被放大，變成粗粗的一片。

D 越高：
  一個 texel 對應牆上較小面積。
  髒斑顆粒會變細。

SPP 越高：
  髒斑會變淡。
  但它主要處理濃淡，並不直接改變一顆髒斑在牆上的大小。

因此目前順序是：

1. 先提高 D，所有候選都維持 1000 SPP，確認髒斑粗度能否變細。
2. D 候選值定下後，若髒斑分布仍不理想，再用 1000 SPP 做取樣品質實驗，例如 blue-noise bake sampler。
3. D 與取樣策略都定下後，最後才跑 10000 SPP，取得正式乾淨牆面。

12. OPUS 審查結論（2026-06-01）

總評：方向 APPROVE。 計畫正確把問題鎖在「粗度＝D/解析度軸」（與 SPP 濃淡軸分開），且把剛建好的 render-space seam gate 設成「每個 D 都要過」、並明訂「解析度變更＝seam re-trigger」——這正是 seam 防呆系統該被用的方式。Metal tiled 安全配置、D 數值（D800≈3379×2327≈1.84×、D1000≈4224×2908≈2.87×，已核對）、D→blue-noise→10000spp 的順序都合理。落地前補四點。

1.（高價值，先預判）edge-policy 修法本身是「解析度相依」的，提高 D 可能讓縫復發

seam 修法的 maxFillPixels = 4 是「固定 texel 數」；但那條 valid-but-black invalid 帶是「固定物理寬度」。D 越高，同一條帶跨越的 texel 數越多 → 4 格回填可能蓋不滿 → 縫在 D800/D1000 復發。

- seam gate 會抓到（很好，這就是它的用途），但要事先預期：
  maxFillPixels 需要「隨 D 縮放」，或改用「物理寬度(mm) → 每個 D 換算 texel」定義。
- 這正是 seam 計畫「解析度變更 re-trigger 邊界」原則，現在套到「修法自己」身上。
  請備好調整，別等 gate 判紅才反應。

2. 高 D 的時間與記憶體（不構成阻擋）

- 烘焙時間（CODEX 量測，依 texel 線性放大）：D590 約 1分54秒；D800 約 3分半；D1000 約 5分半。
  全在 6 分鐘內 → timeout 給普通 hang 護欄即可。
- raw atlas 檔大小：65 / 120 / 187 MB（D590 / D800 / D1000）。
- 烘焙當下記憶體約 3× atlas（rawHdr + averaged + preSync 三份全圖緩衝）→ D1000 約 560MB
  + runtime DataTexture 約 187MB。GPU 單次提交仍被 tile 界定（安全不變）。D1000 留意 JS heap 即可，非硬阻擋。

3.（設定期待）D 改的是「顆粒大小」，不是「雜訊量」

此近距相機下，D800/D1000 會讓顆粒變細，但 texel 多半仍 ≥ 螢幕像素 → 不會產生「多 texel 平均」的去噪效果。所以結果會是「更細」、不會是「乾淨」。這正確、也是預期——「乾淨」來自後面的 blue-noise + 10000spp。A/B 判準（§7.1「顆粒變細」）對準「細」即可，別誤期待「speckle 消失」。

4.（框架校正）blue-noise 是「並行互補」，不只是「D 不夠才補」

D 與 blue-noise 是不同機制的互補（D＝顆粒變細；blue-noise＝把雜訊推到高頻、降低低頻結塊感），最終乾淨版要併用——使用者點出的「並行」是更準的模型。測試階段先隔離 D（方法學上對），但別因 D800「看起來夠好」就把 blue-noise 丟掉，它在任何 D 下都仍有增益。§11 最終版已併用，方向對，僅把「條件式 fallback」框架更正成「co-equal 互補」。

13.1 edge-policy 改成 D-aware

北牆非方格目前的西樑北端接縫修法，原本使用固定 texel 數：

maxFillPixels   = 4
maxSearchPixels = 10

這在 D590 的 2492 × 1716 北牆上已驗收通過。 但提高 D 後，同一條物理寬度的邊界會跨越更多 texel。固定 4 格會變得相對太窄，可能讓縫隙復發。

因此 edge-policy 現在改成「以 D590 尺寸為參考，依新 faceSizePx 自動放大」：

referenceFaceWidthPx  = 2492
referenceFaceHeightPx = 1716

scale = max(currentWidth / 2492, currentHeight / 1716)

maxFillPixels   = ceil(4  × scale)
maxSearchPixels = ceil(10 × scale)

預期換算：

D590  north 2492 × 1716  → fill 4 / search 10
D800  north 約 3379 × 2327 → fill 6 / search 14
D1000 north 約 4224 × 2908 → fill 7 / search 17

重點是：D 變大時，邊界修法跟著變大，不再把 D590 的 4 格硬套到更高解析度。

13.2 gate 清單補上時間、記憶體與接縫

D800 / D1000 每次 throwaway bake 回報時，必須附以下最小數字：

1. targetAtlasWidth / targetAtlasHeight
2. raw atlas 檔案大小

4. contextLost / contextRestored
5. maxSubmissionElapsedMs
6. maxTileReadbackMs

2. minCompletedSamples 必須達到 targetSamples。
3. timedOut 必須是 false。
4. maxSubmissionElapsedMs 與 maxTileReadbackMs 必須維持在 Metal 安全線內。
5. seam gate 必須維持綠燈；解析度變更本身視為 seam re-trigger。

15. OPUS 審查 §14（2026-06-01）

總評：盤點誠實，但核心修法有一個結構性缺口必須先補——目前的「D-aware」在 D800 會變成 no-op。 §14 把已完成／未完成分得清楚，helper 數學本身正確、且在 D590 正確退化成 fill 4（無回歸）。問題出在它縮放的「來源」。已逐行讀碼核實，非採信宣稱。

15.1（CRITICAL，答 Q1／Q4）D-aware 讀到的是「寫死常數」，D800 會算出 scale = 1.0

證據鏈（js/InitCommon.js）：

- :1538-1542 北/東牆非方格幾何 5 個常數全寫死 D590：
    ATLAS_SIZE_PX        = 2912 × 3432
    NORTH_WALL_UV_RECT   = uMax 2492/2912, vMax 1716/3432
    NORTH_WALL_FACE_SIZE = 2492 × 1716
- :1591-1592 policy.referenceFaceWidthPx / HeightPx = 2492 / 1716（同一組數）。
- :2895 / :2900-2901 apply 取 faceWidth/faceHeight ← FACE_SIZE_PX 常數。
- :2910 helper 收到的就是這個常數。
- :2869-2871 widthScale = faceWidth / referenceFaceWidth = 2492 / 2492 = 1.0。
  → 任何 D 都算 scale = 1.0 → maxFillPixels 永遠 = ceil(4 × 1.0) = 4。

helper 是拿「寫死的 face size」除以「寫死的 reference」，兩者都是 2492，比值恆為 1。只有當 FACE_SIZE_PX 常數本身被改成 D800 的值，scale 才會 ≠ 1。

位置也會跟著錯：

- :2904 startX = floor((region.xMax - bounds.xMin)/xSpan × faceWidth)，用 faceWidth = 2492。
- :3351 loader 傳給 apply 的 atlas 尺寸 targetAtlasWidth/Height 是「package 動態值」（D800 變大）。
- D800 北牆 face 實際約 3379 寬，seam 物理位置落在 ~3379 座標系；
  startX 仍以 2492 座標系算 → 回填欄位整個偏左、偏窄。位置與寬度雙錯。

根因＝single source of truth 分裂：atlas 尺寸走 package（動態），face/UV 幾何走寫死常數（靜態），D-aware 程式讀到的是靜態那半。

15.2（答 Q1，修法）兩條可接受路徑，擇一

A. 首選：face 幾何改成「從 package 推導」，消滅分裂。
   faceWidth  = round((uvRect.uMax - uvRect.uMin) × targetAtlasWidth)
   faceHeight = round((uvRect.vMax - uvRect.vMin) × targetAtlasHeight)
   常數只留「比例（UV rect）」，不留絕對像素 → helper 自動隨 D 正確。

B. 若堅持留常數：D800 variant 接線時必須「同時重生」5 個常數，

Q1. D800 throwaway 是否沿用「north D800 + east D590-resampled、垂直堆疊」合併 layout？

Q2. raw atlas → 合併 package 要手工組，還是寫 assembler？

      1. combined atlas 約 3379 × 4043 × 16 bytes，資料量大。
      2. pointer JSON 要同步 byteLength、chunk、sha256、uvRects、faceSizePx。

    assembler 職責：
      1. 讀 OPUS raw north atlas。
      2. 讀現有 east D590 resampled 區塊。
      3. 配置 combined Float32Array。
      4. copy north/east 到指定 rect。
      5. 寫 combined bin / part chunks / pointer JSON。
      6. 跑 uvRect ↔ faceSizePx guard。

Q4. D800 north 精確尺寸是否為 3379 × 2327？

    是。以 D590 現行北牆 faceSizePx 2492 × 1716 為基準：

      width  = round(2492 × 800 / 590) = 3379
      height = round(1716 × 800 / 590) = 2327

Q5. bake 端 faceSizePx 是否用同公式，與 runtime guard 對齊？

    是。faceSizePx 必須等於實際 copy 進 combined atlas 的整數 rect 尺寸。
    uvRects 必須由整數 layout 反推，不由浮點估算先行。

    guard 公式：
      round((uvRect.z - uvRect.x) × combinedAtlasWidth)  === faceSizePx.width
      round((uvRect.w - uvRect.y) × combinedAtlasHeight) === faceSizePx.height

    north:
      round((1 - 0) × 3379) = 3379
      round((2327/4043 - 0) × 4043) = 2327

    east:
      round((2912/3379 - 0) × 3379) = 2912
      round((1 - 2327/4043) × 4043) = 1716

同意 seam gate 工具新增 --non-square-package。這個參數只決定「本次頁面載入哪一份 non-square package」，不改現有三態邏輯。

建議跑法：

D590 pass：
  不帶 --non-square-package，或帶 d590。
  跑現有三態。
  產 D590 seam 數字 + 截圖。

D800 pass：
  帶 --non-square-package=d800-north-preview。
  跑同一組三態。
  產 D800 seam 數字 + 截圖。

比較：
  D590 與 D800 的同視角截圖並排。
  seam 數字分別列出。

這個設計讓 package 選擇成為測試維度，但不把它塞進同一輪三態矩陣。報告會比較乾淨，失敗時也較容易定位。

23.6 Q4：resolver 命名與放置

命名同意使用：

resolveR7310C1NonSquarePackageUrl()

放置建議：

1. 放在 R7310_C1_NON_SQUARE_ATLAS_RUNTIME_PACKAGE_URL 常數附近，
   或放在 non-square loader helper 區塊開頭。

2. fetch 呼叫點只做：
   var packageUrl = resolveR7310C1NonSquarePackageUrl();
   fetch(packageUrl, ...)

3. resolver 內部負責：
   讀 URLSearchParams。
   key/path allowlist。
   fallback 到 R7310_C1_NON_SQUARE_ATLAS_RUNTIME_PACKAGE_URL。
   記錄本次選到的 packageUrl，方便 seam gate log 回報。

4. 不新增全域 setter。
   本輪只需要開頁時選 package。
   動態切換 package 不在本輪範圍。
