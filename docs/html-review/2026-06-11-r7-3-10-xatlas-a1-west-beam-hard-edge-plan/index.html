R7-3.10 XATLAS A1 西樑黑邊調查與修復

R7-3.10 XATLAS A1 西樑北端不自然黑邊調查計畫

日期：2026-06-11 範圍：北牆 A1 XATLAS raw / OIDN 在「西樑北端 × 北牆」交界出現的貼邊硬黑邊與硬梯度。 狀態：只規劃調查；先不改產品程式、不重烤、不做遮醜處理。

1. 目前共識

這次問題的驗收參考是 LIVE 與 D800。使用者已確認兩者在同位置只有自然、柔順的整體變暗，沒有貼邊硬黑線，也沒有一條像切痕的梯度。XATLAS A1 raw / OIDN 出現的硬黑邊屬於異常現象。

本輪調查遵守 systematic-debugging：先收證據、先做 A/B、先分清楚 raw atlas、runtime 取樣、owner route、D800 對照與 OIDN 影響；根因未釘死前，不提出正式修法。

禁止路線如下：

1. 禁止把邊界柔化、羽化或模糊化當作主修法。
2. 禁止用 runtime 回退條帶把 XATLAS 蓋掉。
3. 禁止直接把最邊 texel 拉亮或手工塗亮。
4. 禁止用 dilation borrow、鄰格借值或 alpha 補洞遮掉症狀。
5. 禁止把真實接觸陰影整段抹掉；目標是回到 LIVE / D800 的自然柔順暗化。

2. 已知事實與分歧點

類別 目前事實 判讀狀態
使用者肉眼 LIVE / D800 同位置自然暗化；XATLAS 有貼邊硬黑邊 已確認，作為最高視覺參考
亮帶修復 鐵門旁 jamb 亮帶已由 owner gate 修復 與本題分開
OIDN raw 與 OIDN 在這條邊的形狀相近 OIDN 目前視為放大可見度的旁觀變因
XATLAS metadata 取樣點附近 worldPos / normal / triId / alpha 對齊；normal 約為 (0,0,1) row flip / UV 對應錯位機率下降
XATLAS 邊界 第一個 valid texel 約在 worldX=-1.750000，也就是西樑幾何邊界 高風險點
密度 XATLAS x 向約 0.005m/texel；D800 約 0.00125m/texel XATLAS 每格涵蓋範圍約 4 倍寬
D800 數值分歧 CODEX 量到 D800 x=-1.750 可很暗；CLAUDE 曾量到較亮 必須用同一 sampler / 同一 package / 同一座標重新判決

目前可採信的暫定模型：

1. XATLAS 第一個 valid texel 落在幾何邊界上。
2. 幾何邊界本來會有接觸暗化，但 D800 / LIVE 的過渡很窄、很柔順。
3. XATLAS 的 texel 較寬，可能把極窄的接觸暗化變成肉眼可見的硬階。
4. 也可能是 XATLAS 在邊界 bake 時額外印太深；這一點要靠 D800 同座標量測和 first-hit / visibility 診斷判決。

3. 目前不能先下的結論

1. 不能先宣稱「只是密度太低」。
   原因：若同一世界座標下 D800 明顯比 XATLAS 亮，表示 XATLAS bake 還有額外偏暗來源。

2. 不能先宣稱「XATLAS 邊界 texel 本身印壞」。
   原因：若 D800 在精準幾何邊界同樣很暗，只是只佔極窄範圍，密度與邊界中心位置就仍是主因。

3. 不能把 OIDN 當成主因。
   原因：raw 與 OIDN 都要同時量，若 raw 已有同形硬階，OIDN 只能算後續顯影因素。

4. 不能把鐵門亮帶修法混進本題。
   原因：jamb 亮帶是重複認領加光；西樑北端硬黑邊目前看起來是 XATLAS 邊界 bake / 密度 / 取樣問題。

4. 要回答的核心問題

1. XATLAS 第一個 valid texel 的世界位置，是否正好卡在西樑幾何邊界？
2. D800 在完全相同世界座標、相同 y、高度、相同 package 狀態下，到底是多暗？
3. XATLAS 與 D800 的亮度差，主要來自 texel 寬度、邊界中心位置，還是 bake ray / visibility 判斷？
4. runtime 是否有 owner handoff、source route 或 valid-linear 混值造成額外硬線？
5. 若提高 XATLAS 北牆 A1 密度，硬黑邊是否會自然縮成 D800 那種柔順過渡？

5. 調查階段

5.1 Phase 0：環境鎖定

先把每次量測的網址、package、開關與相機寫進 report，避免再次發生「畫面其實沒走目標路徑」的誤會。

1. 記錄目前 branch、commit、工作樹狀態。
2. 記錄 runtime pointer 與 URL query：
   - XATLAS raw package
   - XATLAS OIDN package
   - D800 raw package
   - D800 OIDN package
3. 記錄 UI 狀態：
   - 北牆烘焙 ON
   - 非方格 ON
   - XATLAS A1 ON / OFF
   - SPP cap
4. 固定使用者提供的西樑北端相機：
   cameraState={"position":{"x":-1.670797,"y":2.496491,"z":-1.77606},"yaw":0.6752,"pitch":0.98,"fov":54,"forward":{"x":-0.348169,"y":0.830497,"z":-0.434802}}
   view={"facing":"上(+Y)","config":1,"samples":54,"paused":false,"sppCap":1000}
5. 每次報告都附上實際 URL；不能只寫「raw」或「OIDN」字串。

5.2 Phase 1：畫面路徑與 source route 證明

同一相機跑四種狀態，先把肉眼現象和 shader 來源釘在一起。

1. LIVE：關 XATLAS / 關 D800 package，走即時光追參考。
2. D800：走 D800 北牆取樣。
3. XATLAS raw：走 XATLAS A1 raw package。
4. XATLAS OIDN：走 XATLAS A1 OIDN package。

每個狀態都要收：

1. 同視角截圖。
2. ROI 亮度剖面，橫跨 `x=-1.755` 到 `x=-1.735`。
3. final source / owner route：確認每個畫素是 west beam、north wall D800、XATLAS A1、LIVE 中哪一條。
4. ownerCount：確認沒有重複認領或 owner 空洞。

5.3 Phase 2：CPU atlas 同座標剖面

用 CPU 直接讀 package，不用易受瀏覽器狀態污染的即時 capture。XATLAS raw / XATLAS OIDN / D800 raw / D800 OIDN 必須走同一座標清單。

y x 座標清單
2.56 -1.755, -1.752, -1.750, -1.748, -1.746, -1.744, -1.740, -1.735
2.60 -1.755, -1.752, -1.750, -1.748, -1.746, -1.744, -1.740, -1.735
2.63 -1.755, -1.752, -1.750, -1.748, -1.746, -1.744, -1.740, -1.735
2.70 -1.755, -1.752, -1.750, -1.748, -1.746, -1.744, -1.740, -1.735

輸出欄位：

1. worldX / worldY / atlasU / atlasV / texel index。
2. luma raw。
3. luma OIDN。
4. alpha / valid。
5. valid-linear 是否跨 invalid。
6. metadata normal / triId / worldPos。

判決條件：

1. 若 D800 在 `x=-1.750` 同樣很暗，但 `x=-1.748` 快速回到正常，XATLAS 主要疑點轉向 texel 寬度與第一格中心位置。
2. 若 D800 在 `x=-1.750` 明顯比 XATLAS 亮，XATLAS bake 邊界第一格有額外偏暗來源。
3. 若 raw 與 OIDN 的剖面同形，OIDN 排出主因，只保留顯影影響。

5.4 Phase 3：XATLAS 邊界 metadata 與幾何關係

針對 XATLAS 第一條 valid texel band，逐格列出 metadata 與幾何邊界距離。

1. 取 `py=216..221`、對應 `worldY≈2.56..2.72`。
2. 取 `px=58..66`，覆蓋西樑邊界附近。
3. 每格列：
   - worldX / worldY / worldZ
   - normal
   - triId
   - alpha
   - luma raw / OIDN
   - 距西樑幾何邊界 `x=-1.75` 的距離
4. 檢查 first valid 的中心是否正好等於、略小於、或略大於 `x=-1.75`。

要釐清的判斷：

1. first valid texel 若中心正卡邊界，XATLAS 可能把邊界極值畫成一整格。
2. first valid texel 若中心已經進入北牆內部，仍遠暗於 D800，同步轉查 bake ray / visibility。
3. metadata 若有 normal、triId 或 worldPos 異常，回到 bake metadata 產生路徑。

5.5 Phase 4：formal runner bake-light 診斷

若 Phase 2 / 3 顯示 XATLAS 邊界第一格有額外偏暗來源，就用正式 runner 診斷 bake 時的光線，不使用先前已證明會污染狀態的即時 capture。

診斷點：

1. XATLAS 邊界格：`worldX≈-1.750`。
2. XATLAS 內部格：`worldX≈-1.745` 或更內側。
3. D800 同世界座標對照。

輸出項目：

1. primary ray origin / direction。
2. first-hit hitType / objectId / normal / position。
3. visibility / occlusion 指標。
4. NEE 幾何項與直接光 / 間接光分量。
5. 是否接觸到 west beam 幾何或 open-air gap。

判決條件：

1. 若邊界格 first-hit / visibility 明顯偏向西樑遮蔽，查 worldPos 是否剛好放在幾何邊界。
2. 若邊界格與內部格光線差異只來自接觸遮蔽範圍太窄，密度方案進入候選。
3. 若正式 runner 指出 sampler / binding / tile 狀態異常，回到 bake pipeline 查。

6. 可能根因樹

H1  邊界中心問題
    XATLAS first valid texel 中心正卡 `x=-1.75`，吃到接觸邊極暗值。

H2  XATLAS texel 密度不足
    真實暗化很窄，D800 / LIVE 能呈現柔順過渡；XATLAS 每格太寬，形成肉眼硬階。

H3  XATLAS bake 邊界額外偏暗
    同世界座標下 D800 比 XATLAS 亮，表示 XATLAS bake ray、visibility 或 chart 邊界處理另有問題。

H4  D800 對照口徑不一致
    CODEX 與 CLAUDE 對 D800 `x=-1.750` 的數值不同；需用同一 sampler、同一 package、同一座標清單重算。

H5  runtime source handoff 異常
    ownerCount 或 final source 在邊界有跳動，造成畫面看起來像黑線。

H6  OIDN 顯影
    raw 已存在硬階，OIDN 只讓它更乾淨、更顯眼；此項只作排除與量化。

7. 可接受的後續修法家族

這一節只列「根因成立後才可評估」的方向，尚未進入實作。

1. 若 H1 / H2 成立：
   - 提高 XATLAS A1 北牆局部 texel 密度，先做 D800 等效密度驗證包。
   - 檢查 chart 邊界 first valid texel 的中心放置規則，讓有效格代表北牆內部，而非幾何交線極值。

2. 若 H3 成立：
   - 查 bake ray origin / visibility / occlusion 的邊界規則。
   - 修正 bake pipeline，使 XATLAS 與 D800 在同世界位置得到一致的自然接觸暗化。

3. 若 H5 成立：
   - 修 owner route 或 source handoff，並用 ownerCount / final-source probe 鎖住。

仍然禁止：

1. 邊界柔化。
2. runtime 回退條帶。
3. 手工拉亮最邊 texel。
4. 用鄰格借值或 alpha 補洞掩蓋。

8. 驗收標準

視覺標準：

1. 使用者提供的西樑北端相機下，XATLAS A1 不再出現貼邊硬黑線。
2. 西樑與北牆交界只保留 LIVE / D800 同等級的自然柔順暗化。
3. 北牆 A1 低處破圖不回歸。
4. 鐵門旁 jamb 亮帶修復不回歸。

數值標準：

1. XATLAS edge profile 與 D800 edge profile 在同世界座標下可解釋。
2. `x=-1.750` 到 `x=-1.748` 的亮度跳變需落在 D800 / LIVE 可接受的自然過渡範圍。
3. raw 與 OIDN 對照能說明 OIDN 影響，不把 OIDN 誤當根因。
4. ownerCount 在 ROI 內維持單一歸屬或明確 live fallback，無重複加光與空洞。

白話摘要：

目前 CODEX 這邊先把 H1 / H2 拉高：邊界中心與密度是主嫌。H3「XATLAS 自己額外印太深」先降級，但還要等 CLAUDE 把 D800 量尺校準完才能最後定案。

仍需 CLAUDE 回答：

1. D800 在 x=-1.750, y=2.60 的正確同座標 luma 到底是多少？
2. CLAUDE 先前的 0.168 是否來自 row flip、rounding、package、UV layout 或半格座標差？

4. 若 D800 exact edge 經校準後明顯比 XATLAS 亮，H3 要重新升級。

帳目零殘差（每個 texel 的歸屬都有交代、無重複無遺漏）是 owner policy 內部一致性的最強證據，比單看任一三角形的百分比更可靠。

14.4 四個審查問題的裁示

問題 1 — 可否作為 XATLAS A1 北牆 promotion 密度規格候選？
  同意列為候選。雙方向 0.00125m 與 D800、與全室 bake 密度規格一致，不會在北牆 A1
  留下獨立的低密度孤島；且修掉了 height4x 的單方向拉伸（各向異性→各向同性）。
  使用者肉眼已確認黑邊消失、髒紋消失、OIDN 平滑、jamb 無復發，且未用任何禁止手段。

問題 2 — 3784×2064 的記憶體／體積／runtime 成本可接受？
  可接受。atlas F32 = 119.2MB（7,810,176 texel），略小於 D800 的 3379×2327 ≈ 120MB；
  D800 已在 runtime 運行，故此量級已實證可行。
  兩點備註（非阻擋項）：
   (a) 有效利用率僅 30.2%（alpha=1 只 2,359,325 / 7,810,176），即 119MB 約 70% 是非 own texel；
       這是 xatlas 打包 + C2C 嚴格判定的固有代價，不是 bug。
   (b) 若 runtime 上傳改用 RGBA16F（half），可由 119MB 砍半至 ~60MB VRAM；
       間接光 radiance 動態範圍（max luma < 1、nonzeroRatio 0.30）通常 half 已足夠，建議 CODEX 評估。
  texel-metadata 357.5MB 僅離線／bake 用，不上 runtime，不計入 runtime 成本。

問題 3 — C2C alpha r64 是否符合既有 owner policy？
  大致符合，附三點：
   (a) rgbNonzeroAlphaZeroTexels = 0（每個 triangle 皆 0）：沒有「有亮度卻被判 invalid」的洩漏，
       代表 owner policy 沒有誤殺北牆可見亮區——這是最重要的正面證據。
   (b) 帳目零殘差（見 14.3），owner 判定內部一致。
   (c) tri20 / tri21 各 19,456 texel 全 alpha=0：光從 report 無法定位世界座標。
       promotion 前請 CODEX 用 texel-metadata 確認這兩個 chart 確實落在 side-wall／門洞／西樑 gap
       隱藏區（正確不 own），而非誤殺北牆可見區。

問題 4 — 還需要 first-valid texel center 內縮規則，或 full4x 密度已足夠？
  對「西樑北端 × 北牆」這一條邊：full4x 密度已足夠，使用者肉眼已確認，不需再疊內縮規則。
  但「內縮」作為通用 promotion 規則仍有獨立價值：密度提高只是把黑邊縮到 0.00125m（與 D800 同寬、
  肉眼看不見），並未消除「第一個有效 texel 中心壓在幾何折線上取到極值」這個機制本身。
  裁示：promotion 規格先釘 A（高變化區強制 full4x 等效密度）；
        B（邊界 texel 內縮）降級為「未達等效密度的 chart 的回退保護規則」，
        不必為北牆 A1 這條邊立即實作。此判斷與 §11／§12 的「A＋B 雙規則」共識一致，
        差別是 full4x 證明了 A 單獨即可解這條邊。

16.2 owner 機制補完（promotion 須知，非 §15 糾錯）

CODEX §15 對 tri20/21 的陳述全部正確。我額外做了一次全域掃描，補完整條 gap 的 owner 圖像：

掃「全部 alpha=1 的 texel，其 worldPos 是否落入 westBeamGap(x[-1.908,-1.752] y[2.525,2.905])」：
  → 506,257 個 alpha=1 texel 落在 gap 矩形內（首個樣本屬 tri11，非 tri20/21）。

意義：atlas 並未把整條 gap 清零；gap 內仍有大量 alpha=1 texel（多屬 tri11／tri14 等北牆主三角）。 gap 區的「不顯示」實際由 runtime gate 負責——已讀 glsl:1207–1251 確認：

glsl:1239  if (r7310C1NorthWallHiddenByBeamGap(visiblePosition.x, visiblePosition.y))
              { atlasUv = vec2(0.0); return false; }   // 命中點落 gap → 不取 atlas

因此 owner 是「雙層」：

第一層 runtime gate（範圍框 glsl:1221 x[-1.912,-1.518] + side-wall + 門洞 + beam-gap）：
        負責 gap／門洞／側牆的「即時不顯示」。
第二層 atlas backface-ratio mask：
        把 bake 視角看不到北牆的 texel（如 tri20/21，西樑背面）設 alpha=0。
tri20/21 alpha=0 的直接原因是第二層（backface mask），與「落在 gap」相關，
但 atlas 清零的機制不是 gap gate。

16.3 promotion 影響

1. runtime gate r7310C1NorthWallHiddenByBeamGap (glsl:1239) 必須保留。
   不可因「C2C alpha 已處理 owner」而移除：atlas 沒清零 gap，gap 內有 506,257 個 alpha=1 texel。
   若移除 gate，gap 邊界的 bilinear 取樣會把這些 texel 取進來，gap 區可能顯示北牆 radiance（破圖風險）。
   （此為 code + data 推論；未實測「移除 gate 的畫面」。）
2. 建議 §15 補一句：owner 為「runtime gate + atlas backface mask」雙層，兩者不可互相取代。
3. tri20/21 結論不變、promotion 不受影響——本節是機制文件化，不是阻擋項。
